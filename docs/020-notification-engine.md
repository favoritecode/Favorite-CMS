# 1. Purpose



This document defines the architecture, responsibilities, boundaries, and public interfaces of the Favorite CMS Notification Engine.



The Notification Engine is responsible for creating, routing, and delivering approved platform notifications.



Notifications may communicate relevant information to Users, administrators, or other approved recipients without embedding delivery-provider logic directly into unrelated Engines or Plugins.



---



# 2. Notification Engine Objectives



The Notification Engine must provide a foundation for:



* Notification Definition

* Notification Creation

* Recipient Resolution

* Notification Routing

* Delivery Channel Resolution

* Delivery Status

* Notification Failure Handling

* User Notification Integration

* Plugin Notification Integration

* Queue and Event Integration



The exact notification provider, transport, external service, and delivery technology remain behind approved Notification Engine interfaces.



---



# 3. Notification



A Notification represents an approved message or alert generated by the platform.



A Notification may represent:



* Account-related information

* Content-related information

* Media-related information

* System-related information

* Plugin-defined information

* Other explicitly approved platform communication



The Notification Engine must not automatically generate notifications for every platform event.



Notification creation must be explicit and controlled.



---



# 4. Notification Identifier



Every Notification must have a stable Notification Identifier.



The Notification Identifier may be used to:



* Track Notification state

* Reference delivery attempts

* Record delivery results

* Support diagnostics

* Associate a Notification with its recipient or source context



The exact identifier format is implementation-specific.



---



# 5. Notification Payload



A Notification contains approved data required to communicate the message.



The Payload may include:



* Notification type

* Recipient reference

* Title or subject data

* Message data

* Related resource reference

* Approved metadata

* Delivery context



The Notification Payload must contain only the information necessary for the approved Notification contract.



Sensitive data must not be included unnecessarily.



---



# 6. Notification Recipient



A Notification Recipient is the approved target of a Notification.



A Recipient may be represented by:



* User reference

* Administrator reference

* Approved recipient address or destination

* Other explicitly supported recipient identity



Recipient resolution must remain separate from unrelated business logic.



---



# 7. Notification Producer



A Notification Producer is an Engine or approved Plugin that requests creation of a Notification.



The Producer is responsible for:



* Selecting the correct Notification type

* Providing the approved Payload

* Providing or resolving the intended Recipient

* Using the public Notification Engine interface



The Producer remains responsible for the business occurrence that caused the Notification.



---



# 8. Delivery Channel



A Delivery Channel represents an approved method through which a Notification may be delivered.



Possible channel categories may include:



* In-application notification

* Email

* Push notification

* SMS or similar messaging

* Other explicitly supported channels



This document does not require any specific external delivery provider.



Channels must be implemented behind approved interfaces.



---



# 9. Notification Boundary



The Notification Engine owns Notification coordination and delivery state.



It does not own the business resource that caused the Notification.



Therefore:



User Engine

→ Owns User state.



Content Engine

→ Owns Content state.



Media Engine

→ Owns Media state.



Plugin

→ Owns Plugin business logic.



Notification Engine

→ Creates and delivers approved Notifications.



A Notification must not become the source of truth for the underlying resource.

# 10. Notification Creation



A Notification Producer creates a Notification through the approved Notification Engine interface.



The creation process must:



1\. Identify the Notification type.

2\. Validate the Notification Payload.

3\. Resolve the intended Recipient.

4\. Determine the applicable Delivery Channel.

5\. Create the Notification record or equivalent reference.

6\. Return a normalized creation result.



Notification creation must remain separate from unrelated business logic.



---



# 11. Notification Validation



Before a Notification is accepted, the Notification Engine must validate:



* Notification type

* Required Payload fields

* Recipient information

* Delivery Channel requirements

* Required metadata

* Applicable authorization requirements



An invalid Notification must not be treated as successfully created.



---



# 12. Recipient Resolution



The Notification Engine must resolve the intended Recipient through approved interfaces.



Recipient resolution may use:



* User identity

* Administrator identity

* Approved destination information

* Other explicitly supported recipient references



A Notification must not be delivered to an unintended Recipient because of ambiguous or incomplete resolution.



---



# 13. Delivery Channel Resolution



The Notification Engine must determine which approved Delivery Channel applies to the Notification.



Channel resolution may depend on:



* Notification type

* Recipient context

* User settings

* Platform configuration

* Plugin configuration

* Other explicitly approved rules



The Notification Engine must not assume that every Notification supports every Delivery Channel.



---



# 14. Notification Delivery



The Notification Engine is responsible for coordinating delivery through the selected Delivery Channel.



The general delivery flow is:



Notification Created

→ Recipient Resolved

→ Channel Resolved

→ Delivery Requested

→ Delivery Result Recorded



The exact transport mechanism remains implementation-specific.



---



# 15. Delivery Adapter Boundary



External or internal delivery implementations must remain behind approved Delivery Channel interfaces.



A Delivery Adapter may handle communication with a supported delivery mechanism.



The Notification Engine must not require unrelated Engines or Plugins to know provider-specific implementation details.



---



# 16. Delivery Status



A Notification may have a delivery state such as:



* Pending

* Delivered

* Failed



Additional states may be introduced only when explicitly required by the Notification contract.



The Notification Engine must provide a normalized representation of delivery state.



---



# 17. Delivery Failure



A Notification delivery attempt may fail because of:



* Invalid Recipient

* Unsupported Channel

* Delivery Adapter failure

* Provider failure

* Network failure

* Authorization failure

* Other approved delivery errors



A failed delivery must not be reported as successfully delivered.



---



# 18. Delivery Retry Boundary



The Notification Engine may support controlled retry behavior for failed deliveries.



Retry behavior must be explicitly defined by the applicable Notification or Delivery Channel contract.



The Notification Engine must not retry failed deliveries indefinitely unless an approved policy explicitly requires it.



Repeated delivery attempts must avoid unintended duplicate communication where applicable.

# 19. Notification and User Engine



The User Engine may provide identity, profile, and preference context required for approved Notification delivery.



The Notification Engine must not become the owner of User data.



User-related Notification behavior must respect:



* User identity

* User visibility rules

* User settings

* Applicable Permission requirements



The User Engine remains the source of truth for User state.



---



# 20. Notification Preferences



The Notification Engine may respect approved User or platform Notification preferences.



Preferences may determine:



* Whether a Notification should be delivered

* Which Delivery Channel is allowed

* Whether a Notification category is enabled

* Other explicitly supported delivery choices



The exact preference storage model remains outside this document unless defined by the Settings Engine or another approved specification.



---



# 21. Notification and Permission Engine



Protected Notification operations must respect applicable Permission rules.



A Notification Producer must not use the Notification Engine to bypass authorization.



Where required, Permission checks may apply to:



* Notification creation

* Recipient access

* Administrative Notification management

* Protected Notification data

* Plugin-defined Notification operations



The Permission Engine remains responsible for authorization decisions.



---



# 22. Notification and Event Engine



The Event Engine may trigger approved Notification workflows.



Example:



Source Engine

→ Publishes Event



Event Engine

→ Delivers Event



Approved Consumer

→ Requests Notification



Notification Engine

→ Creates and routes Notification



The Event Engine must not automatically generate Notifications unless an approved Consumer explicitly performs that action.



---



# 23. Notification and Queue Engine



The Queue Engine may be used for deferred Notification delivery.



Example:



Notification Created

→ Delivery Job submitted



Queue Engine

→ Executes delivery Job



Notification Engine

→ Records delivery result



The Queue Engine manages deferred execution.



The Notification Engine remains responsible for Notification state and delivery coordination.



---



# 24. Notification and Content Engine



The Content Engine may request approved Notifications for Content-related occurrences.



The Notification Engine must not modify Content state.



A Notification may reference Content by an approved resource identifier.



The Content Engine remains responsible for Content lifecycle and data.



---



# 25. Notification and Media Engine



The Media Engine may request approved Notifications for Media-related occurrences.



The Notification Engine must not modify Media Resources or Media lifecycle.



A Notification may reference Media through approved resource relationships when required.



---



# 26. Notification and Plugin Boundary



Plugins may create approved Notifications through public Notification Engine interfaces.



A Plugin may:



* Register approved Notification types.

* Request Notification creation.

* Provide approved Notification data.

* Integrate with supported Notification workflows.



A Plugin must not:



* Modify Notification Engine internals.

* Read unrelated private Notifications.

* Bypass Recipient isolation.

* Bypass Permission checks.

* Depend directly on undocumented delivery providers.

* Send protected data through unapproved channels.



---



# 27. Notification Isolation



Notifications must remain isolated by recipient and applicable scope.



A Notification intended for one Recipient must not be exposed to another Recipient unless explicitly permitted.



Plugin Notifications must not expose another Plugin's private Notification data.



Notification isolation must preserve platform security boundaries.



---



# 28. Notification Failure Isolation



Notification failure must not corrupt the source resource.



For example:



Failed email delivery

→ Must not corrupt User state.



Failed push delivery

→ Must not corrupt Content.



Failed Plugin Notification

→ Must not corrupt another Plugin.



The Notification Engine must treat delivery failure separately from the business operation that caused the Notification.

# 29. Notification Security Boundary



The Notification Engine must treat Notification content and delivery information as controlled platform data.



A Notification must not expose:



* Authentication credentials

* Private session information

* Unrelated User data

* Internal secrets

* Private implementation details



Only information required by the approved Notification contract may be included.



---



# 30. Notification Authorization



Notification operations may require authorization.



Authorization may apply to:



* Notification creation

* Notification management

* Recipient access

* Administrative delivery actions

* Plugin-defined Notification operations



The Notification Engine must not treat Notification creation or delivery as a replacement for Permission evaluation.



---



# 31. Notification Ownership



The Notification Engine owns Notification coordination and delivery state.



It does not own the resource that caused the Notification.



For example:



Content Notification

→ Content Engine owns Content.



Media Notification

→ Media Engine owns Media.



User Notification

→ User Engine owns User state.



Plugin Notification

→ Plugin owns its business responsibility.



Notification Engine

→ Owns Notification delivery coordination.



---



# 32. Notification Registration



Approved Notification types must be registered through public Notification Engine interfaces.



A Notification registration may define:



* Notification type

* Approved Producer

* Payload contract

* Recipient requirements

* Supported Delivery Channels

* Delivery requirements

* Retry behavior when applicable



Private Notification Engine internals must not be modified directly by Producers or Plugins.



---



# 33. Notification Lifecycle



The general Notification lifecycle is:



Create

→ Validate

→ Resolve Recipient

→ Resolve Channel

→ Deliver or Queue

→ Record Result

→ Complete or Fail



The exact internal implementation may vary.



The public Notification contract must remain stable.



---



# 34. Read State Boundary



In-application Notifications may support a presentation or interaction state such as:



* Unread

* Read



Additional interaction states may be added only when explicitly required.



Read state must remain separate from the underlying business resource state.



Marking a Notification as read must not modify the source Content, Media, User, or Plugin resource.



---



# 35. Notification Dismissal Boundary



The platform may support dismissal or removal of a Notification from a User-facing view.



Dismissal must affect only the Notification representation or applicable Notification state.



It must not delete or modify the source resource that caused the Notification.



---



# 36. Notification Observability



The Notification Engine may provide controlled operational information such as:



* Notification Created

* Notification Routed

* Delivery Started

* Delivery Completed

* Delivery Failed

* Delivery Retried

* Notification Read

* Notification Dismissed



Operational information must not expose protected Notification Payload data unnecessarily.



---



# 37. Notification Recovery



The Notification Engine should recover safely from supported delivery or infrastructure failures.



Recovery behavior may include:



* Controlled retry

* Marking delivery as Failed

* Preserving delivery diagnostics

* Allowing approved manual recovery



The exact recovery mechanism remains implementation-specific.



---



# 38. Notification Compatibility



Changes to the internal Notification Engine implementation must preserve the public Notification contract when the change is non-breaking.



Existing Producers, Plugins, recipients, and Delivery Channel integrations must remain compatible with supported Notification Engine versions.



Breaking changes must follow the project's versioning and migration rules.



---



# 39. Notification Engine Non-Goals



The Notification Engine does not own:



* User Resources

* Content Resources

* Media Resources

* Search Indexes

* Cache Entries

* Event definitions

* Queue Jobs

* Permission rules

* Theme resources

* Plugin business logic

* Source-resource storage



The Notification Engine is responsible for approved Notification creation, routing, delivery coordination, and Notification state.

# 40. Final Notification Resolution Rules



The Notification Engine must process Notifications through approved public interfaces.



The general Notification flow is:



1\. Create the Notification.

2\. Validate the Notification type.

3\. Validate the Notification Payload.

4\. Resolve the intended Recipient.

5\. Resolve the applicable Delivery Channel.

6\. Evaluate required authorization or preference rules.

7\. Deliver immediately or submit approved deferred work.

8\. Record the delivery result.

9\. Retry only when explicitly allowed.

10\. Record final Notification state.



The Notification Engine must not become the source of truth for the business resource that caused the Notification.



---



# 41. Notification Contract



Every Notification must follow an approved Notification contract.



The contract must define:



* Notification type

* Notification purpose

* Approved Producer

* Approved Payload structure

* Recipient requirements

* Supported Delivery Channels

* Authorization requirements when applicable

* Delivery requirements

* Retry behavior when applicable

* Compatibility requirements



Notification consumers and Delivery Adapters must not depend on data outside the approved contract.



---



# 42. Producer Contract



A Notification Producer must:



* Create only approved Notification types.

* Build valid Notification Payloads.

* Provide or resolve an approved Recipient.

* Avoid exposing unrelated sensitive data.

* Preserve ownership of the source resource.

* Use the public Notification Engine interface.



Creating a Notification must not transfer business responsibility to the Notification Engine.



---



# 43. Delivery Channel Contract



Every Delivery Channel must operate through an approved interface.



A Delivery Channel implementation must:



* Accept approved Notification data.

* Validate required delivery information.

* Return a normalized delivery result.

* Report delivery failures accurately.

* Protect sensitive Notification information.

* Avoid exposing provider-specific implementation details to unrelated Engines or Plugins.



The Notification Engine must remain independent from any specific delivery provider.



---



# 44. Recipient Isolation Contract



Notification delivery must preserve Recipient isolation.



A Notification intended for one Recipient must not be exposed to another Recipient unless explicitly authorized.



Recipient-specific data must remain isolated across:



* Users

* Administrators

* Plugin contexts

* Delivery Channels

* Other protected Notification scopes



---



# 45. Preference Contract



Where Notification preferences are supported, the Notification Engine must respect the applicable approved preference rules.



A preference may affect:



* Notification eligibility

* Delivery Channel selection

* Notification category delivery

* Other explicitly supported behavior



Preferences must not silently override mandatory platform Notifications unless the applicable contract explicitly allows it.



The exact preference storage implementation remains outside this document.



---



# 46. Event and Queue Coordination Contract



The Notification Engine may integrate with the Event Engine and Queue Engine without merging their responsibilities.



Preferred flow:



Source Engine

→ Event Engine

→ Approved Consumer

→ Notification Engine



For deferred delivery:



Notification Engine

→ Queue Engine

→ Delivery Work

→ Notification Engine records result



The Event Engine communicates occurrences.



The Queue Engine coordinates deferred execution.



The Notification Engine owns Notification coordination and delivery state.



---



# 47. Plugin Notification Contract



Plugins may register and create approved Notifications through public interfaces.



Plugin Notification behavior must remain isolated.



A Plugin must not:



* Modify Notification Engine internals.

* Access another Plugin's private Notifications.

* Access unrelated User Notifications.

* Bypass Permission checks.

* Bypass Recipient isolation.

* Use unsupported Delivery Channels.

* Depend directly on undocumented delivery providers.

* Expose protected data through Notification Payloads.



---



# 48. Notification Failure Contract



Notification processing must fail safely.



A Notification failure must not automatically:



* Corrupt the source resource.

* Corrupt User state.

* Corrupt Content or Media.

* Corrupt unrelated Notifications.

* Corrupt another Plugin.

* Expose protected Notification information.

* Report failed delivery as successful delivery.



The Notification Engine must provide a controlled failure result.



---



# 49. Codex Implementation Rules



When implementing the Notification Engine, Codex must:



* Follow the frozen architecture from Documents 001–019.

* Follow the defined folder structure.

* Use approved public interfaces.

* Preserve User Engine ownership.

* Preserve Content Engine ownership.

* Preserve Media Engine ownership.

* Preserve Permission Engine boundaries.

* Preserve Event Engine boundaries.

* Preserve Queue Engine boundaries.

* Preserve Plugin isolation.

* Preserve Recipient isolation.

* Keep Notification Payloads minimal and contract-driven.

* Keep provider-specific delivery logic behind adapters or equivalent approved interfaces.

* Avoid inventing undocumented Notification types.

* Avoid introducing a specific email provider, SMS provider, push provider, messaging provider, or external Notification service as an architectural requirement.

* Avoid assuming unsupported delivery, retry, read-state, dismissal, or scheduling behavior.



If an implementation detail is not defined by this document, Codex must not silently introduce a conflicting Notification architecture.

# 51. Document Status



This document defines the Notification Engine specification for Favorite CMS.



The Notification Engine must be implemented according to this document and the frozen architecture established by Documents 001–019.



The Notification Engine provides controlled creation, routing, delivery coordination, and state management for approved platform Notifications.



It must not become the owner or source of truth for User, Content, Media, Plugin, or other business resources.



No specific email provider, push provider, SMS provider, messaging service, external Notification platform, or delivery technology is required by this document unless a future architecture document explicitly defines one.



Any future breaking change to the Notification Engine must follow the project's versioning and migration rules.
