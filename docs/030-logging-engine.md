# 1. Purpose



This document defines the architecture, responsibilities, boundaries, and public interfaces of the Favorite CMS Logging Engine.



The Logging Engine provides a controlled platform capability for recording operational information generated by Core, Engines, Plugins, Themes, background operations, and other approved components.



Logging must support:



* Development diagnostics

* Production troubleshooting

* Operational visibility

* Failure investigation

* Security-aware diagnostics

* Plugin and Engine isolation

* Future observability integrations



The Logging Engine must remain separate from business logic, error recovery policy, and resource ownership.



---



# 2. Logging Engine Objectives



The Logging Engine must provide a foundation for:



* Structured Log Records

* Log Levels

* Log Categories

* Log Sources

* Log Context

* Request-aware Logging

* Engine Logging

* Plugin Logging

* Background Job Logging

* Error Logging

* Security-sensitive Data Protection

* Log Output Abstraction

* Log Filtering

* Log Formatting

* Log Retention Boundary

* Logging Failure Isolation

* Observability Integration



The exact logging library, storage implementation, external aggregation service, or monitoring provider must remain implementation-specific unless another approved specification explicitly defines one.



---



# 3. Log Record



A Log Record represents one normalized operational record generated by an approved platform component.



A Log Record may contain:



* Timestamp

* Log Level

* Message

* Log Source

* Log Category

* Request reference when applicable

* Route reference when applicable

* Engine reference when applicable

* Plugin reference when applicable

* Job reference when applicable

* Operation reference when applicable

* Error reference when applicable

* Approved contextual metadata

* Other explicitly supported fields



A Log Record must contain only information necessary for its operational purpose.



---



# 4. Log Identifier



A Log Record may have a unique or traceable identifier when required by the implementation.



A Log Identifier may be used for:



* Diagnostic correlation

* Error investigation

* Request tracing

* Operational tooling

* Support workflows

* Other approved observability purposes



The exact identifier generation strategy remains implementation-specific.



Consumers must not depend on undocumented Log Identifier formats.



---



# 5. Log Level



A Log Level represents the operational severity or importance of a Log Record.



The Logging Engine must support a controlled Log Level model.



Conceptual severity groups may include:



* Diagnostic information

* Normal operational information

* Warning conditions

* Recoverable failures

* Severe failures



The exact Log Level names, numeric values, and mappings must be defined by the implementation contract.



Codex must not invent undocumented severity mappings across unrelated components.



---



# 6. Log Category



A Log Category represents the operational area associated with a Log Record.



A category may represent:



* Core

* Engine

* Plugin

* Theme

* Request

* Routing

* API

* Authentication

* Permission

* Storage

* Queue

* Notification

* Update

* Other approved operational areas



Categories help organize operational records.



They must not replace component ownership.



---



# 7. Log Source



Every Log Record should identify its approved source when applicable.



A Log Source may identify:



* Core component

* Engine

* Plugin

* Theme-related subsystem

* API operation

* Routing operation

* Queue worker

* Scheduled operation

* Update operation

* Other approved component



Log Source identity should remain stable enough to support diagnostics and filtering.



---



# 8. Log Message



A Log Message contains the human-readable operational description associated with a Log Record.



A Log Message should:



* Describe the relevant operational occurrence.

* Avoid unnecessary sensitive information.

* Avoid exposing Credentials.

* Avoid exposing raw security secrets.

* Remain understandable without requiring private implementation knowledge.



Business data must not be copied into logs unless explicitly required and safe.



---



# 9. Log Context



Log Context contains approved structured metadata associated with a Log Record.



Log Context may include:



* Request Identifier

* Route Identifier

* Component Identifier

* Engine Identifier

* Plugin Identifier

* Job Identifier

* Operation Identifier

* Error Identifier

* User reference when explicitly safe

* Locale reference when operationally relevant

* Other approved diagnostic metadata



Log Context must not become a container for arbitrary application state.



---



# 10. Structured Logging



The Logging Engine should support structured Log Records instead of relying entirely on unstructured text.



Preferred conceptual structure:



Log Level



* Source

* Category

* Message

* Context

&#x20; → Normalized Log Record



Structured logging supports:



* Filtering

* Searching

* Correlation

* Diagnostics

* Aggregation

* Future monitoring integration



The exact serialization format remains implementation-specific.



---



# 11. Logging Interface



Platform components must write operational logs through approved Logging Engine interfaces.



Preferred architecture:



Core, Engine, Plugin, or Approved Component

→ Logging Interface

→ Logging Engine

→ Active Log Output



not:



Component

→ Provider-specific Logging SDK



Components must not require direct knowledge of external logging providers when a platform abstraction exists.



---



# 12. Log Output



A Log Output represents an approved destination or handler for normalized Log Records.



A Log Output may conceptually represent:



* Console output

* Local file output

* Structured application output

* External aggregation output

* Other approved destination



The Logging Engine must coordinate Log Outputs through approved interfaces.



No single output destination is required by this document.



---



# 13. Multiple Log Outputs



The Logging Engine may support more than one active Log Output when explicitly configured.



For example, one deployment may conceptually use:



Logging Engine

→ Console Output

→ Persistent Output



while another deployment may use:



Logging Engine

→ Structured External Output



The exact output configuration must remain deployment-specific.



Platform components must not depend on the number of active outputs.



---



# 14. Logging Ownership Boundary



The Logging Engine owns:



* Log Record normalization

* Logging interfaces

* Log Source handling

* Log Category handling

* Log Context handling

* Log output coordination

* Log filtering support

* Logging failure isolation



The Logging Engine does not own:



* Business operations

* Error recovery policy

* Authentication policy

* Permission policy

* Resource state

* Plugin business logic

* Queue execution

* Update decisions

* Security policy

* Backup policy



Logging records operational behavior.



It must not control business behavior merely because an operation was logged.

# 15. Log Filtering



The Logging Engine must support controlled filtering of Log Records.



Filtering may consider:



* Log Level

* Log Category

* Log Source

* Engine Identifier

* Plugin Identifier

* Request Identifier

* Job Identifier

* Other approved Log Context



Filtering must affect Log handling only.



It must not change the underlying business operation.



---



# 16. Log Level Filtering



Deployments may choose which Log Levels are processed by active Log Outputs.



For example:



Development Environment

→ May retain more diagnostic information.



Production Environment

→ May restrict unnecessary diagnostic output.



The exact enabled Log Levels must be configuration-driven.



Platform components must not hard-code environment-specific Log filtering when the Logging Engine provides an approved configuration path.



---



# 17. Log Source Filtering



The Logging Engine may support filtering by Log Source.



Source filtering may help isolate:



* Core activity

* Engine activity

* Plugin activity

* Queue operations

* API activity

* Routing activity

* Update activity

* Other approved components



Disabling output for one source must not disable the source component itself.



---



# 18. Request-aware Logging



The Logging Engine may associate Log Records with an approved Request Identifier.



Preferred flow:



Incoming Request

→ Request Context

→ Request Identifier

→ Engine or Plugin Operations

→ Log Records

→ Shared Request Correlation



Request-aware Logging enables multiple operational records from one request to be correlated.



Raw request bodies, Credentials, or sensitive headers must not automatically be copied into Log Context.



---



# 19. Route-aware Logging



When applicable, Log Records may include a stable Route Identifier.



Route-aware Logging may help diagnose:



* Route resolution

* API dispatch

* Rendering dispatch

* Route failures

* Plugin Route behavior

* Administrative Route behavior



The Logging Engine must not require logging the complete raw URL when an approved stable Route Identifier is sufficient.



---



# 20. User-aware Logging Boundary



A Log Record may contain a User reference only when operationally necessary and explicitly safe.



User-aware Logging must avoid exposing unnecessary personal information.



Preferred behavior:



User Context

→ Stable approved User reference

→ Log Context



not:



User Context

→ Full User profile

→ Log Record



The Logging Engine must preserve User privacy boundaries.



---

* Authentication operation started

* Authentication Context invalid

* Authentication provider unavailable



Logs must not contain:



* Raw passwords

* Raw Credentials

* Sensitive Token values

* Session secrets

* Private authentication keys



Authentication logging must remain diagnostic, not credential storage.

Permission-related Logging may include:



* Permission evaluation completed

* Protected operation denied

* Invalid Permission Context

* Permission configuration failure



Permission logs must not expose unrelated protected Resource data.



The Logging Engine must not determine whether Permission should be granted.

# 24. Routing Logging

* Route matched

# 25. Engine Logging



Platform Engines must use the approved Logging interface for operational diagnostics.



An Engine may log:



* Lifecycle operations

* Validation failures

* Dependency failures

* Controlled warnings

* Internal operational state transitions

* Other approved diagnostic information



Engine logs must not expose private implementation data beyond what is required for diagnostics.



---



# 26. Plugin Logging



Plugins may use the Logging Engine through approved public interfaces.



Plugin Log Records should identify the Plugin as the source.



A Plugin must not:



* Write directly into another Plugin's private logs.

* Impersonate another Plugin's Log Source.

* Bypass sensitive-data protections.

* Depend directly on an external logging provider when a platform Logging abstraction exists.



Broken Plugin Logging must not destabilize the Logging Engine.



---



# 27. Theme Logging Boundary



Themes may produce limited diagnostic Log Records when explicitly supported.



Theme logging should remain presentation-focused.



A Theme must not use Logging as a hidden persistent storage mechanism.



A Theme must not expose:



* Sensitive User data

* Credentials

* Private Plugin state

* Protected Settings



Theme-related logging must remain optional and controlled.

The Logging Engine must record errors without becoming responsible for deciding how they are recovered.

→ Applicable Error Handling Contract

→ Normalized Error Information

→ Logging Engine

→ Log Record



The Logging Engine must not independently alter application control flow because an error was logged.

# 39. Exception Logging Boundary

* User data

* Protected payloads

* Provider-specific sensitive information

# 42. Sensitive Data Protection



The Logging Engine must protect sensitive information by default.



Sensitive data may include:



* Passwords

* Raw Credentials

* Authentication Tokens

* Session secrets

* API secrets

* Provider Credentials

* Private configuration

* Payment-related sensitive data

* Protected User data

* Private Plugin data

* Other explicitly protected information



Sensitive data must not be written into Log Records unless an approved security contract explicitly permits it.



---



# 43. Log Redaction



The Logging Engine may support redaction of sensitive or restricted values before a Log Record is delivered to an output.



Redaction may apply to:



* Credentials

* Tokens

* Secret keys

* Protected headers

* Sensitive query values

* Private identifiers

* Other approved fields



The exact redaction rules must be defined by configuration or security contracts.



Codex must not invent unsafe redaction behavior.



---



# 44. Log Data Minimization



Log Records should contain only information required for operational diagnostics.



Components must avoid logging:



* Entire Resource payloads

* Full User profiles

* Complete request bodies

* Complete response bodies

* Full database records

* File contents

* Private Plugin configuration

* Other unnecessary application state



Logging must favor minimal structured context over excessive data capture.



---



# 45. Logging Security Boundary



The Logging Engine must preserve security boundaries across all supported components.



Logging must not become a method to bypass:



* Permission rules

* Authentication boundaries

* Plugin isolation

* User privacy

* Storage security

* Configuration secrecy

* Resource visibility rules



Operational visibility must not override application confidentiality.



---



# 46. Log Output Security



Every active Log Output must preserve the security guarantees of the Logging Engine.



An Output must not silently expose protected Log Records to an unauthorized destination.



Output configuration must be validated before activation.



A misconfigured external output must fail safely.



---



# 47. Log Output Failure



A Log Output may become unavailable or fail during operation.



Possible failures may include:



* File output unavailable

* External output unavailable

* Network failure

* Invalid output configuration

* Serialization failure

* Output permission failure

* Other infrastructure failures



An Output failure must not automatically crash the business operation that generated the Log Record.



---



# 48. Logging Failure Isolation



Logging failures must remain isolated from unrelated platform behavior wherever possible.



For example:



External Log Output unavailable

→ Must not prevent Content creation.



Plugin Log failure

→ Must not crash the Plugin business operation.



Log serialization failure

→ Must not crash Core.



Logging configuration failure

→ Must not expose secrets.



Logging is operational support infrastructure and must fail safely.



---



# 49. Logging Reliability Boundary



The Logging Engine should make a reasonable effort to deliver approved Log Records.



However, business correctness must not depend on successful Log delivery unless another approved contract explicitly defines an audit-critical requirement.



The Logging Engine must not silently become a transactional business datastore.



---



# 50. Log Retention Boundary

Retention may consider:



* Environment

* Log severity

* Operational requirements

* Other explicitly approved rules



The Logging Engine must not invent permanent retention requirements.



Exact retention periods must be defined by operational policy.

# 51. Log Cleanup

Cleanup behavior must:



* Follow configured retention rules.

* Remain isolated from application Resource deletion.

The exact cleanup implementation remains deployment-specific.

# 58. Final Logging Flow



The Logging Engine must process Log Records through approved public interfaces.



The general logging flow is:



1\. Receive a logging request from an approved component.

2\. Resolve the Log Source.

3\. Resolve the Log Category.

4\. Resolve the Log Level.

5\. Normalize the Log Message.

6\. Normalize approved Log Context.

7\. Apply sensitive-data protections.

8\. Apply configured filtering rules.

9\. Build the normalized Log Record.

10\. Dispatch the Log Record to approved active Log Outputs.

11\. Handle output failures safely.



Logging must remain isolated from business execution wherever possible.

# 61. Sensitive Logging Contract



Sensitive information must be protected before Log Records reach any output.



The Logging Engine and producing components must not intentionally log:



* Raw passwords

* Raw authentication Credentials

* Sensitive Token values

* Session secrets

* Provider secrets

* API secrets

* Encryption secrets

* Private configuration values

* Protected User data without explicit operational justification

* Private Resource contents without explicit approval



Sensitive-data safety takes priority over diagnostic convenience.



---



# 62. Component Logging Contract



Core, Engines, Plugins, and approved platform components must use the public Logging interface.



A component must:



* Identify its Log Source accurately.

* Use appropriate Log Categories.

* Provide only necessary diagnostic context.

* Avoid sensitive data.

* Follow configured Logging behavior.

* Handle Logging failure safely.



A component must not:



* Impersonate another component's Log Source.

* Directly depend on output-specific implementation.

* Treat logs as business persistence.

* Assume that successful business behavior requires successful Log delivery.



---



# 63. Plugin Logging Contract



Plugins must remain isolated when using the Logging Engine.



A Plugin must:



* Identify itself through an approved Plugin Source.

* Preserve sensitive-data boundaries.

* Avoid logging another Plugin's private state.

* Use approved Logging interfaces.

* Handle Logging failures safely.



A Plugin must not:



* Modify Logging Engine internals.

* Register unsafe outputs without an approved extension contract.

* Override another Plugin's logging identity.

* Use Logging to bypass Plugin storage isolation.



---



# 64. Error Logging Contract



Errors may be recorded through the Logging Engine after safe normalization.



Preferred flow:



Operation Failure

→ Error Handling Contract

→ Safe Error Information

→ Logging Engine

→ Structured Error Log



The Logging Engine must not decide:



* Whether the operation should retry.

* Whether the transaction should rollback.

* Whether the User should receive a specific error.

* Whether the application should recover.



Those responsibilities belong to the applicable Error Handling and owning-component contracts.



---



# 65. Output Contract



Every Log Output must implement the approved output interface.



An Output must:



* Accept normalized Log Records.

* Respect configured filtering.

* Preserve sensitive-data protections.

* Return controlled failure when unavailable.

* Avoid changing business behavior.



Output-specific implementation details must remain behind the Logging Engine.



---



# 66. Logging Configuration Contract

Logging configuration may control:



* Enabled Log Levels

* Enabled Log Sources

* Enabled Categories

* Redaction behavior

---



# 67. Logging Failure Contract



Logging must fail safely.



A Logging failure must not automatically:



* Abort Content creation.

* Abort Media processing.

* Abort User operations.

* Abort Plugin operations.

* Abort Queue Jobs.

* Crash Core.

* Crash the Admin environment.

* Crash the public site.

* Expose protected data.

* Corrupt application Resources.



Where Logging itself fails, the application must preserve the primary operation according to the applicable owning-component contract.



---



# 68. Logging Security Contract



The Logging Engine must preserve platform confidentiality and isolation.



Logging must not bypass:



* Authentication boundaries

* Permission boundaries

* Plugin isolation

* User privacy

* Storage security

* Configuration secrecy

* Resource visibility



Operational diagnostics must remain subordinate to platform security.



---



# 69. Provider Independence Contract



The Favorite CMS Logging architecture must remain independent of one specific logging provider.



The platform may support different outputs in different environments.



For example:



Development

→ Local or console-oriented output.



Production

→ Persistent or external structured output.



These are implementation choices.



Core, Engines, and Plugins must continue to use the same approved Logging interface regardless of the active output technology.



---



# 70. Codex Implementation Rules



When implementing the Logging Engine, Codex must:



* Follow the frozen architecture from Documents 001–029.

* Follow the defined folder structure.

* Use approved public interfaces.

* Keep Logging separate from business logic.

* Keep Logging separate from Error recovery.

* Preserve Engine ownership boundaries.

* Preserve Plugin isolation.

* Preserve User privacy.

* Preserve Authentication boundaries.

* Preserve Permission boundaries.

* Preserve Storage security boundaries.

* Preserve API security boundaries.

* Preserve Queue boundaries.

* Preserve Update Engine boundaries.

* Use structured Log Records.

* Use stable Log Source identities.

* Use approved Log Context only.

* Support correlation references where explicitly applicable.

* Apply sensitive-data protection before output.

* Keep Log Outputs behind an abstraction.

* Keep output failure isolated.

* Keep environment-specific Logging behavior configuration-driven.

* Never log raw passwords.

* Never log raw Credentials.

* Never log sensitive Token values.

* Never log secrets merely for convenience.

* Never automatically serialize full exception objects without safety filtering.

* Never automatically log full request or response bodies.

* Never treat logs as a transactional database.

* Never make business correctness depend on Log Output availability unless another approved audit contract explicitly requires it.

* Never hard-code one external logging provider as a permanent platform dependency.

* Never allow a Plugin to impersonate another Plugin's Log Source.



If an implementation detail is not defined by this document, Codex must not silently introduce a conflicting Logging architecture.

# 72. Document Status



This document defines the Logging Engine specification for Favorite CMS.



The Logging Engine must be implemented according to this document and the frozen architecture established by Documents 001–029.



The Logging Engine provides structured operational logging, component-aware context, request and job correlation, sensitive-data protection, Log filtering, output abstraction, provider independence, and Logging failure isolation.



The Logging Engine must remain an operational infrastructure capability.



It must not become the owner of business state, Error recovery policy, Authentication policy, Permission policy, Plugin business logic, Queue execution, monitoring policy, or audit policy.



No specific logging library, external logging provider, aggregation service, monitoring platform, storage backend, or observability vendor is required by this document unless another approved architecture specification explicitly defines one.



Any future breaking change to the Logging Engine must follow the project's versioning and migration rules.
